2026 年春天，一个英文单词在开发者社区里忽然火起来。一个月前还很少人提，一个月后已经出现在各平台技术帖和文章里里。这个词就是 Harness Engineering。

有意思的地方是，越多人讨论它，它就越难被讲清楚。有人说它是"马具工程"，有人说它是"驾驭工程"，有人说它是上下文工程的放大版，有人说它是软件工程思想在 AI 时代的回魂，还有人干脆认定这又是一次新瓶装旧酒。各种说法之间口径不一，有时候还互相矛盾。顺着几篇不同作者的文章读下来，很容易越读越糊涂。

本文不打算给这个词一个"最终定义"。定义是结论，来龙去脉才是理解的起点。一个术语为什么会在某个时刻出现，是谁提出来的，它想解决什么问题，它和已有概念的边界在哪里——这些问题搞清楚了，"它到底是什么"反而变成一个顺带能回答的小问题。

## 一、一个词是怎么出现的

讨论任何一个新术语，从时间线开始总是比较清醒的做法。

这个词的第一次正式亮相，是在 2026 年 2 月 5 日。那一天，HashiCorp 的联合创始人 Mitchell Hashimoto 在个人博客上发表了一篇长文，标题叫《My AI Adoption Journey》。他在文章里提出了一个说法："Engineer the harness"。这句话本身没有展开成严格定义，它更像是 Mitchell 对自己这一年使用 AI 编码工具的总结。他的意思很朴素：每次发现 Agent 犯了一个错，就花时间设计一个解决方案，让它永远不再犯同样的错。

这个思路听起来有点像反复调校一个实习生。Mitchell 的重点不在于训练模型，而在改造模型周围的环境。他花时间改的不是 prompt，也不是模型权重，是工具、规则、脚手架。他不相信靠重写提示词能让模型变得可靠，他相信的是补齐外围基础设施，让模型在犯错的路径上撞墙。

六天后，OpenAI 发表了一篇工程博客，标题直白得吓人：《Harness Engineering: Leveraging Codex in an Agent-First World》，作者 Ryan Lopopolo。

这篇文章的分量要比 Mitchell 的博客重得多。它不是个人随笔，是 OpenAI 团队对自己如何在生产环境中使用 Codex 的经验总结。文章里列了一堆实际做法：AGENTS.md 怎么写，plan 目录如何组织，工具如何暴露，Git worktree 怎么用，自定义 linter 如何在错误信息里嵌入修复指令，CI 怎么当作 Agent 输出的质量闸门。每一条都不复杂，但合起来指向同一个工程态度：让 Agent 真正干活的，不是模型有多聪明，而是模型外面的那一整套架子有多结实。

这篇文章让 harness engineering 第一次走出小圈子。它也把 Mitchell 那个抽象说法落实成了具体做法。人们想找一个完整案例来理解"到底什么叫 engineer the harness"的时候，有了一个可以指的东西。

一个半月后，3 月 24 日，Anthropic 发表了自己的版本：一篇讨论长时运行 Agent 的 harness 设计研究，题目叫《Effective harnesses for long-running agents》（也有版本叫《Harness design for long-running application development》）。

Anthropic 讲的是另外一类问题：当你希望一个 Agent 连续工作很多个小时，跨越多个 session 完成一个复杂任务，harness 应该怎么设计才能让它不在中途崩掉。他们给出的方案包括 planner-generator-evaluator 三代理架构，用 progress.txt 文件记录跨 session 状态，把执行计划和已完成计划都纳入版本控制等等。

Anthropic 文章里有一句话后来被很多人引用：

> 每一个 harness 组件都编码了一个关于"模型自身做不到什么"的假设，而这些假设是值得反复检验的：它们可能本来就是错的，也可能会随着模型的进步很快过时。

这句话提醒读者，harness 不是一劳永逸的架构。它是围绕模型当下能力边界搭起来的临时脚手架，脚手架的每一根支柱都可能被下一代模型拆掉。

到了 3 月底，又一件事给这个词的流行加了把火。3 月 31 日，安全研究员 Chaofan Shou 发现 npm registry 上的 @anthropic-ai/claude-code 包存在一个构建配置失误，Claude Code 的完整源码通过 source map 泄露出来。这件事在技术社区引起了巨大反响，披露推文获得了超过 1700 万次浏览。一夜之间，数不清的开发者涌进去阅读源码，逐行分析这套一直被视为"harness 设计典范"的系统到底是怎么构造的。

在此之前，关于 harness engineering 的讨论大多停留在博客、推文和二手经验分享层面。在此之后，人们可以看到一个已经跑出十亿美元年化收入的生产级 Agent 系统内部究竟长什么样。控制面在哪一层，query loop 怎么运转，工具权限如何校验，上下文怎么压缩，错误如何恢复。这些问题突然有了可以逐行对照的答案。

围绕 harness engineering 的讨论，到这时候才真正开始深入。

## 二、补考：其实它并不完全是 2026 年的发明

词源考古做到这里，事情似乎已经很清楚了。Mitchell 2 月 5 日提概念，OpenAI 2 月 11 日用案例让它出圈，Anthropic 3 月 24 日给出进阶研究，Claude Code 源码泄露在 3 月底推向高潮。一条看起来很整洁的时间线。

但只看这条时间线，会漏掉一段更早的铺垫。

早在 2025 年 3 月，也就是上面这条时间线开始前的将近一年，知名开发者 swyx 就在一系列文章里提出过相似的说法。他当时叫它 "agent engineering"，并配了一个叫 IMPACT 的框架。IMPACT 是六个词的首字母：Intent（用户意图和表达）、Memory（跨 session 的记忆）、Planning（任务拆解和规划）、Authority（自主决策和用户介入的边界）、Control Flow（由 LLM 驱动的控制流）、Tools（Agent 能调用的工具集）。

把这六个维度放在一起看，你会发现它和 2026 年那几篇 harness engineering 的核心议题几乎完全重合。Intent 对应指令设计，Memory 对应上下文治理，Planning 对应任务拆解，Authority 对应权限判定，Control Flow 对应运行时循环，Tools 对应工具系统。当时这个框架没有"出圈"，大家顺手用了一阵子，没形成像 harness engineering 这样朗朗上口的标签，也没有发生类似 Claude Code 源码泄露这样的事件来催化讨论。

这不是一个偶然的前传。它说明一件事：这个领域的问题意识其实已经酝酿了很久，只是需要一个合适的时机、一个生动的词和一组具体案例，才能变成一个能被广泛讨论的公共话题。Mitchell 的那句 "engineer the harness" 之所以后来被放大，不是因为它比 IMPACT 更深刻，而是它抓住了一个好用的比喻，这个比喻又恰好出现在社区已经积累了足够多共识的那个节点。

严格来说，harness engineering 不是哪个人或哪家公司的发明。它是社区在几乎同一段时间，从不同方向逼近同一个问题之后，自然形成的一个收敛点。Mitchell 的个人实践、swyx 的早期框架、OpenAI 的工程报告、Anthropic 的研究文章、Claude Code 源码公开、linux.do 和 Medium 上的大量讨论，共同构成了这个词的"诞生环境"。

这一点对后面理解定义之争很重要。如果它是某一家公司独立发明的概念，那它的"正确解释"自然归这家公司所有；但它不是。它是一场群体性的命名过程，所以围绕它会产生三种不同的理解口径，这件事本身就很自然。

## 三、三种解释口径

看市面上各种关于 harness engineering 的解读，我把他们大致可以归为三派。三派的差异不只是措辞不同，它们背后对"模型应该被怎样对待"这个问题有相当不同的立场。

### 马具派

这个口径的来源很直观。Harness 这个英文单词本意就是马具或者挽具，是人类给马穿戴的那一套装备。所以当 Mitchell 说 "engineer the harness" 的时候，字面上就能翻译成"好好打造你的那套马具"。马具派认为，这个比喻已经足够说明问题：模型像一匹好马，力气大但不守规矩，harness 是给它穿上的装备，让骑手能够驾驭它。Opus 4.6、GPT-5、Gemini 3 这些顶级模型是赤兔马，Claude Code、Codex 这些系统是马镫和缰绳。同样的赤兔马，在会骑马的人手里是战神，在不会骑马的人手里是摔伤事故。

这个口径直观好懂，适合做比喻，适合写公众号标题，适合向不熟悉 AI 的读者解释这件事到底在说什么。它的问题在隐喻本身带了一层被动意味：马是被驾驭的对象，harness 是约束它的装备。这层意味让一部分开发者觉得不舒服，他们认为这种比喻暗示了一种"压制模型潜力"的态度。

### 工作空间派

这一派对"马具"那层被动意味有直接的反对意见。

他们的核心主张是：harness 的目的不是限制模型能做什么，而是创造条件让模型能做到原本做不到的事。一个没有合适工作环境的熟练工人是做不出好活的。原因不是他能力不够，是没有趁手的工具、没有可靠的原材料、没有可以参考的图纸、没有可以反馈质量的检测工序。给他准备好这些东西，是赋能而不是束缚。

这个视角下，harness engineering 的意义在于定义协作边界和协作协议，让模型能在一个稳定、可交互、可反馈的环境里持续工作。这一派经常会追溯到上下文工程（context engineering）的思路：他们认为 harness 本质上是"相关上下文"这一类型的延伸，是在回答一个问题，怎样让模型在执行每一步的时候，都能拿到它需要的那部分上下文，既不多也不少。

这个口径的好处是把关注点放回到"让系统能做出更多事"这个积极面上，和很多 Agent 产品构建者的直觉更贴合。它的风险是有时候会过于乐观，容易淡化一个事实：模型会犯错，这些错误在 shell、文件系统、Git 这些真实环境里会留下真实后果。

### 约束执行派

这一派在关于 Claude Code 源码的系统性研究里表达得最充分。

起点是一个冷峻的判断：模型是不稳定部件，甚至是整个系统里最不稳定的部件。人们喜欢把 Agent 想象成一个见习工程师，会写代码，会调工具，会在终端里独立工作，似乎只要再多训练一下就能变成正式员工。但一旦它能接触 shell、Git、网络和本地文件，问题就从"它答得好不好"变成"它执行留下的后果怎么收拾"。

从这个视角出发，harness engineering 的意义就很直接：一整套制度化的控制平面，用来处理一个现实问题，模型并不天然值得信任。所以 harness 的每一个组件都不是装饰，都围绕"约束执行"展开。system prompt 是行为协议，query loop 是运行时心跳，tool schema 是受管执行接口，context compact 是工作内存治理，permission 是授权边界，hook 是生命周期钩子。它们合在一起，构成一个结构化的约束系统，让一个本质上不稳定的模型被折进一套可持续运行的工程秩序里。

这一派的代表观点可以浓缩成一句话：

> 代理系统的关键能力是约束执行。

这句话听起来比马具派更严厉，比工作空间派更悲观，但它最接近 Claude Code 源码在实现上呈现出来的态度。

三派的分歧值得额外说一下：它们并不矛盾，只是重心不同。马具派更关心"怎么描述这件事让别人听得懂"；工作空间派更关心"怎么描述这件事让自己建起来的系统更有野心"；约束执行派更关心"怎么描述这件事让自己的系统不会在生产环境里翻车"。三种关心都合理，适用的场合不一样。

写教程文章的作者用马具派的语言更容易开场。创业公司里从零搭 Agent 产品的工程师用工作空间派的语言更能向同事解释自己在做什么。在大厂负责一个已经跑在生产里的 Agent 系统的团队负责人用约束执行派的语言更能说服管理层批准把时间花在那些"看起来像补丁"的基础设施上。

如果一定要选一种作为默认理解，约束执行派大概是最安全的那种。原因也很朴素：系统是给未来的自己写的，未来的自己总会遇到今天还没看见的问题，而约束结构在面对未知故障的时候，比漂亮的比喻更管用。

## 四、它和 prompt engineering、context engineering 是什么关系

既然这个词有三种解释口径，那它和已有工程术语的边界就值得澄清一下。尤其是两个最容易和它混在一起的词：prompt engineering 和 context engineering。

一种流传比较广的说法是把这三个词视为一个递进阶梯。

最早是 prompt engineering。那时候大家关心的是单次对话里怎么措辞才能让模型给出更好的输出。早期那些"AI 提效技巧"文章讲的都是这件事：给模型一个角色，给它一组示例，给它一个输出格式。这些技巧在 GPT-3.5 和 GPT-4 早期确实有效，那个阶段的模型对提示词的敏感度很高，一个好的 prompt 能让它从"勉强能用"变成"相当不错"。

第二个阶段是 context engineering。随着模型能力提升和任务变复杂，人们发现单纯改提示词已经不够了。影响输出质量的，是进入模型 context window 的那一堆 token 整体上是什么样的。相关文档有没有，历史对话要不要压缩，工具描述怎么组织，外部知识怎么检索进来。Anthropic 在《Effective context engineering for AI agents》里给过一个还算清晰的定义：context engineering 关心的是在有限的上下文窗口里，选择、组织并注入与任务高度相关的信息，让大语言模型能够在合理的边界内做出最佳推理和执行。这个阶段的关注点从"这一句话怎么写"转向了"这一整窗内容怎么拼"。

第三个阶段就是 harness engineering。它的关注点又往外扩了一层。不是单次对话，也不是 context window 本身，是 Agent 的整个运行环境。这个环境包括工具、权限、状态持久化、错误恢复、多代理协作、验证机制、团队制度。harness engineering 把整个运行环境纳入工程化管理的范畴，要求开发者对 Agent 能接触什么、能做什么、犯错时会怎样、跨会话如何保持一致这些问题做出显式的设计决策。

这个递进关系有一个朴素的直觉：模型越强，问题就越往外移。模型很弱的时候，写好一句 prompt 就能大幅改善结果；模型中等强的时候，把上下文组织好才能让它发挥出完整能力；模型已经很强的时候，决定成败的已经不是模型本身，是包裹模型的那一整套工程结构。

不过这个阶梯论也有人持保留意见。有观点认为把三者描述成"一代更比一代强"的递进关系，会掩盖它们之间的重叠和互补。prompt engineering 的原则并没有过时，它只是变成了一个更大系统里的子模块。harness engineering 里面的每一个具体组件都依然要依赖好的 prompt 和好的上下文选择。这三件事更像是同一栋建筑的三层楼板，而不是接力赛里的三棒选手。

社区里还流行一个简短的公式，最早由 LangChain 的工程师 Viv Trivedy 在《The Anatomy of an Agent Harness》里推广：

```
Agent = Model + Harness
```

按照这个公式，一个裸模型只是一个概率生成器，被 harness 包裹之后才能称作 Agent。harness 提供状态、工具执行、反馈闭环和可以被强制执行的约束。这些东西加起来，让一堆 next-token prediction 变成一个能独立完成任务的系统。

公式虽然简单，它解释了一件常被忽略的事：Agent 不是一个模型类别，是一种系统形态。决定它行为的不是模型本身，是包裹模型的那套东西。同一个 Claude 4.6，放在 Claude Code 里和放在一个简陋脚手架里，行为表现可以差得非常远。差距不在权重，在 harness。

## 五、harness 的"器官系统"

把概念关系理清之后，下一个自然的问题是：一个 harness 具体包含哪些组件？不同作者的列法略有出入，但如果把几篇有代表性的文章对齐看，会发现大家其实在同一套器官系统上打转。

最基础的是 **system prompt 与指令分层**。这不是传统意义上那种"你是一个有帮助的助手"式的人格设定，是一套分层的运行时规章。Claude Code 源码里可以看到，它的 system prompt 被拆成多段：身份与总任务在一段，工具与权限说明在另一段，工程约束（不要越权、不要谎报验证、不要为了省事发明抽象）又在另一段。这些段落还要按优先级组装，默认 prompt、自定义 prompt、agent prompt、append prompt，每一层都有清楚的覆盖关系。把 prompt 当作控制面的一部分，而不是一段文字魔法，是 harness engineering 和传统 prompt engineering 的一个明确分界。

接下来是 **query loop**，也就是运行时主循环。一个 Agent 不是"请求-响应"式的问答系统，它是一段持续运行的循环。Claude Code 的核心不是某一次 API 调用，是一个带状态的循环体：messages、tool use context、compact tracking、turn count、transition。每一轮执行留下的状态会进入下一轮，系统要在这个循环里持续处理消息裁剪、工具结果预算、压缩、中断、恢复。没有这个循环，所谓 Agent 就只是一个带工具的 chatbot。

然后是 **工具系统**。工具包括本地函数调用、Skills、MCP server、外部 API。在 harness 的视角下，工具不是模型能力的自然延伸，是需要被调度、被授权、被限制并发、被审计的受管执行单元。Claude Code 会根据工具的 schema 判断它是否可以并发执行，会对高风险工具（比如 Bash）施加高密度的行为规约，会把执行前的权限询问做成一个独立的阶段，而不是一个随手的检查。

**上下文治理**是另一个关键器官。它包括工作记忆、长期记忆、压缩策略、会话状态的跨轮维护。对话变长、工具输出变多、子任务变复杂的时候，上下文一定会膨胀，系统必须有明确的策略决定什么该留下、什么该压缩、什么该丢弃，压缩的时候如何保留继续工作的语义底座。Anthropic 把这件事叫做 context compact。它不是可选优化，是长时运行 Agent 能不能活下去的关键器官。

**权限与沙箱**决定了模型犯错时会留下多大的后果。是让它直接在宿主机上跑，还是在一个 Docker 沙箱里跑；是让它自动执行所有 shell 命令，还是对高危命令弹出确认窗口；是允许它访问任意路径，还是把它限制在项目目录内。Codex 在这一点上走得更远，它把审批和执行限制做成了一个叫 execpolicy 的单独 crate，里面有 Policy、Rule、Evaluation、Decision 等概念，接近一门小小的政策语言。

**错误恢复**常常被忽略。很多传统软件把失败当作异常处理，Agent 系统不能这样做。对 Agent 来说，失败是日常天气：模型会超 token，会触发 prompt too long，会撞上 max output tokens，会遇到工具拒绝、用户打断、hook 阻塞、API 重试。一个成熟的 harness 必须把这些失败路径当作主路径来设计，预先定义好截断后如何续写、压缩失败时如何让系统恢复呼吸、死循环出现时如何熔断。

**多代理编排与验证**回答的是另一个问题：一个任务如果需要拆解、研究、实现、验证四个阶段，系统该怎么组织？是让同一个 Agent 把所有阶段跑完，还是让不同的 Agent 各司其职？多代理不等于更好，但在某些场景下确实有必要，尤其是验证环节。一个实现者天然倾向于相信自己的改动"差不多行了"，模型更是如此。所以比较稳妥的做法是让验证成为独立阶段，最好由独立的代理角色承担。

最后是 **本地规则与 hook**。这包括 CLAUDE.md、AGENTS.md 这类项目级配置文件，也包括 pre-commit hook、session-start hook、subagent-context hook 这类生命周期钩子。它们的作用是让"组织习惯"能够被写进系统，新来的开发者不用重新学习一遍这个项目的规矩，每次对话都能自动带上项目的上下文约束。

这八个器官不是独立的模块。它们共同构成一个循环系统：prompt 定义行为协议，query loop 负责执行，工具系统决定能触碰什么，上下文治理决定记忆如何流动，权限决定错误后果的范围，恢复机制处理错误本身，多代理把不确定性分区，本地规则把经验沉淀下来。少了其中任何一个，系统的某个方向上就会漏风。

## 六、三层划分：通用、项目、任务

列出八个器官还不足以让这个概念落地。因为同样是"工具系统"这一个器官，它到底应该由使用者自己构建还是应该由 Agent runtime 提供，答案取决于你在哪一层看这件事。

社区里有一个相当实用的划分，把 harness 按照与具体项目的关联程度分成三层。这个分法最早在 linux.do 的一篇讨论帖里被比较清晰地表达出来。

**通用 harness 层**和具体项目弱相关，属于 Agent runtime 或 framework 的通用能力。包括终端交互、tool loop、权限系统、记忆、线程持久化、context compaction、hook 机制、任务调度。各大 Agent CLI——Claude Code、Codex、OpenCode——已经在这一层做了大量工作。对绝大多数开发者来说，这一层不需要自己动手，选一个合适的工具就可以。在这一层做贡献的是 Anthropic 和 OpenAI 这样的基础设施公司，以及 OpenCode 这样的开源项目。

**项目 harness 层**和具体项目强相关，但不是业务功能本身。包括 AGENTS.md 或 CLAUDE.md、仓库的知识布局、架构边界定义、lint 规则、质量标准、依赖选择原则、文档索引。OpenAI 那篇 Codex 工程报告里最有参考价值的经验，大部分集中在这一层。比如他们提到的"AGENTS.md 保持在 100 行以内，作为目录而不是百科全书"，"架构不变量通过自定义 linter 强制执行，错误信息本身就包含修复指令"，"执行计划被视为一流工件，活跃计划、已完成计划和已知技术债务都进行版本控制"。这一层是开发者要操心的地方，也是"我的项目要不要做 harness engineering"这个问题的主战场。

**任务 harness 层**和当前这次具体工作强相关。例如 Anthropic 设计的 planner-generator-evaluator 三 Agent 架构，跨 session 的文档交接机制，针对特定任务的 QA prompt，Playwright 检查脚本。这一层的 harness 往往是任务临时搭起来的，完成之后可能就拆了。它的意义在于为一次特别重要或特别复杂的工作提供额外支架，而不是作为长期基础设施存在。

这个三层划分的实用价值在于，它能帮开发者快速定位自己到底应该操心什么。对一个个人开发者来说，通用层已经由工具提供，不需要自己造；任务层是一次性的，不用做成通用基础设施；长期值得投入的是项目层，写好 CLAUDE.md，配好 lint，定义清楚目录结构，把反复出现的规则沉淀下来。

这个划分还有一个附带好处：它能防止一种常见误解，以为写了一个 CLAUDE.md 就等于"做了 harness engineering"。写 CLAUDE.md 只是项目 harness 层的入口，它解决不了通用层的运行时问题（那是工具的职责），也替代不了任务层的具体编排（那是具体活儿的职责）。三层各司其职，少了任何一层都会出问题，混为一谈也会出问题。

## 七、为什么是 2026 年初

到这里，关于 harness engineering 的来龙去脉基本讲完了。还剩最后一个值得讨论的问题：为什么是 2026 年初？为什么不是 2024 年，也不是 2027 年？

答案和任何术语流行的原因一样，既有偶然也有必然。

偶然的部分是那几个标志性事件的时间集中度。Mitchell 的博客、OpenAI 的工程报告、Anthropic 的研究文章、Claude Code 源码泄露，全都发生在两个月之内。这种密度本身就能让一个词迅速获得传播势能。如果这四件事分散在一年里发生，每一件的影响力都会被稀释，这个词可能就不会像现在这样集中爆发。

必然的部分更值得说。让这个词在这个时间点成立的，是 AI coding 领域的主要矛盾变了。

2023 年或 2024 年初的时候，模型能力还没到一个让人放心的水平。写代码经常写错，上下文理解经常跑偏，工具调用经常失败。那个阶段开发者关心的问题是"模型到底能不能用"。围绕这个问题的讨论集中在模型本身和 prompt 技巧上：怎么让 GPT-3.5 给出更靠谱的答案，怎么让 GPT-4 理解一个大文件，怎么用 few-shot 降低幻觉。那时候 prompt engineering 是主要话题，因为模型本身是瓶颈。

2024 年下半年到 2025 年，情况开始变化。Claude 3.5 Sonnet 这类模型在多文件编辑、代码理解、长上下文这些方向上明显跨过了一道坎。Cursor 这类 AI IDE 开始实用化，Vibe Coding 这个词开始流行。这个阶段的关键问题变成了"怎么把合适的信息喂给模型"。讨论集中在上下文管理上：怎么做 RAG，怎么建知识库，怎么组织大型代码仓库的索引。context engineering 成为主要话题，因为上下文拼装是瓶颈。

2025 年底和 2026 年初，又一道坎被跨过了。Opus 4.6、GPT-5.4 一代模型的能力已经足够强，强到单次推理的质量不再是主要瓶颈。开始出问题的地方变成了长期运行中的系统性失败：Agent 能写出很好的代码，但它会修一个 bug 引入另一个；它能写出很长的代码，但它会在半路把上下文耗光；它能执行复杂任务，但它会在两次 session 之间丢失所有状态；它能给出漂亮的验证报告，但它会把自己的实现判为通过。这些问题不是 prompt 能解决的，也不是光靠堆上下文能解决的。它们需要运行时纪律，需要制度化的约束，需要外部验证，需要跨会话的状态管理。

主要矛盾从"模型够不够聪明"变成了"系统能不能让聪明的模型稳定地做事"。harness engineering 之所以在这个时间点爆发，是因为社区终于有了一个共识：这件事的瓶颈已经不在模型一侧了。

Claude Code 源码泄露加速了这个共识的形成。在此之前，开发者对"一个生产级 Agent 系统长什么样"只能靠想象；在此之后，他们可以逐行看到一个已经跑出十亿美元年化收入的系统内部如何处理这些问题。看完之后的普遍反应是：原来让 Claude Code 比直接调模型强那么多的，不是模型本身，是外面的那一圈脚手架。"那一圈脚手架"这种东西，就是 harness engineering 要讨论的对象。

## 八、最后

回到开头那个问题：harness engineering 到底是什么？

经过前面几节的铺垫，这个问题现在可以被回答得比较克制。

它是一个在 2026 年初由 Mitchell Hashimoto、OpenAI、Anthropic 和社区共同催生的工程术语，背后的问题意识至少可以追溯到 2025 年 swyx 的 agent engineering 框架。它关心的是模型外围的那一整套运行结构：system prompt 与指令分层、query loop、工具系统、上下文治理、权限与沙箱、错误恢复、多代理编排、本地规则与 hook。这些东西合在一起决定了一个 Agent 系统能不能从"可以演示"走到"可以交付"。

它和 prompt engineering、context engineering 的关系更像是三层楼板，而不是三代拳王。每一层都依然存在，只是关注点从一句话的措辞扩展到了整个运行环境的组织。如果一定要用一个公式概括，那就是 Agent = Model + Harness。裸模型是一个概率生成器，它需要被 harness 包裹之后才能称作 Agent。

对它的解释在社区里有三种不同的口径。马具派强调比喻的直观性，工作空间派强调赋能的积极性，约束执行派强调约束的必要性。三种口径都有自己的适用场合，它们之间的分歧本身也是这个术语的一部分。

在实践层面，它可以被拆成三层。通用 harness 层由 Claude Code、Codex、OpenCode 这样的工具提供；项目 harness 层由开发者自己搭建，是长期要投入的地方；任务 harness 层是为特定工作临时搭起来的支架。三层各司其职，混为一谈会出问题。

这篇文章只讲清楚了"是什么"，没有回答一个更重要的问题：为什么必须要它？这个问题的答案藏在那些没有 harness 保护就会发生的具体崩溃里。Agent 不守规矩，修 A 坏 B，上下文腐朽，跨会话失忆，任务膨胀。每一种崩溃都对应 harness 的一个具体器官。把这些崩溃场景讲清楚，就能理解为什么前面列出的那些看起来琐碎的组件，其实一个都不能少。
