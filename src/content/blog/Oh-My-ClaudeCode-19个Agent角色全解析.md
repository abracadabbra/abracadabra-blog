## 前言

上一篇文章讲了 Oh My ClaudeCode 的 Team 模式流水线，今天深入聊聊它的 **19 个专业 Agent**。

一个人写代码，靠的是个人能力。一个团队写代码，靠的是分工协作。OMC 的核心设计哲学就是：**让 AI 像真正的开发团队一样工作**——有架构师、有开发者、有测试员、有审查员，甚至还有专门挑刺的批评者。

## Agent 体系全景

OMC 把 19 个 Agent 分成 **4 个通道**：

```
┌─────────────────────────────────────────────────────────────┐
│                    OMC Agent 体系                            │
├─────────────────────────────────────────────────────────────┤
│  🔨 构建/分析通道    →  从探索到实现的完整开发链路              │
│  🔍 审查通道        →  代码质量和安全把关                     │
│  🎯 领域通道        →  专业领域专家                           │
│  🎭 协调通道        →  挑战和质疑                             │
└─────────────────────────────────────────────────────────────┘
```

每个通道负责不同的工作阶段，组合起来就是一条完整的开发流水线。

## 🔨 构建/分析通道

这是核心开发链路，覆盖从代码探索到最终验证的全流程：

```
explore → analyst → planner → architect → executor → debugger → verifier → tracer
```

### explore（探索者）

| 属性 | 值 |
|------|-----|
| **默认模型** | Haiku（低成本） |
| **职责** | 代码库发现、文件/符号映射 |

探索者是项目的"侦察兵"，负责快速了解代码库结构：

- 扫描项目目录结构
- 识别关键文件和模块
- 建立符号索引（函数、类、变量）
- 生成代码地图

```bash
@explore 找到所有与用户认证相关的文件
@explore 列出 src/api/ 下的所有路由定义
```

**为什么用 Haiku**：探索是高频操作，不需要深度推理，快速便宜即可。

---

### analyst（分析师）

| 属性 | 值 |
|------|-----|
| **默认模型** | Opus（高质量） |
| **职责** | 需求分析、发现隐藏约束 |

分析师负责"想清楚再动手"：

- 分析任务的隐含需求
- 发现边界条件和约束
- 识别潜在风险
- 输出结构化的需求文档

```bash
@analyst 分析 OAuth2 集成的隐藏约束
@analyst 这个支付流程有哪些合规要求？
```

**为什么用 Opus**：需求分析需要深度推理，遗漏约束会导致后续返工。磨刀不误砍柴工。

---

### planner（规划者）

| 属性 | 值 |
|------|-----|
| **默认模型** | Opus（高质量） |
| **职责** | 任务排序、创建执行计划 |

规划者把大任务拆解成可执行的小任务：

```
任务：实现用户认证系统

执行计划：
├── 阶段 1（并行）
│   ├── 子任务 A：设计数据库 schema
│   └── 子任务 B：实现 JWT 工具类
├── 阶段 2（依赖 A, B）
│   ├── 子任务 C：实现注册接口
│   └── 子任务 D：实现登录接口
└── 阶段 3（依赖 C, D）
    └── 子任务 E：编写集成测试
```

**关键能力**：识别哪些任务可以并行，哪些必须串行。这直接决定了执行效率。

---

### architect（架构师）

| 属性 | 值 |
|------|-----|
| **默认模型** | Opus（高质量） |
| **职责** | 系统设计、接口定义、权衡分析 |

架构师关注"怎么做"，而不是"做什么"：

- 设计模块架构
- 定义接口契约
- 分析技术选型的权衡
- 输出架构图和设计文档

```bash
@architect 设计一个支持水平扩展的认证架构
@architect 微服务之间应该如何通信？REST vs gRPC？
```

**与 analyst 的区别**：
- `analyst`：这个支付系统需要支持哪些支付方式？（需求）
- `architect`：支付模块应该怎么设计？用策略模式还是工厂模式？（设计）

---

### executor（执行者）⭐ 最常用

| 属性 | 值 |
|------|-----|
| **默认模型** | Sonnet（平衡） |
| **职责** | 代码实现、重构 |

执行者是干活的主力，Team 模式下可以有多个 executor 并行工作：

```bash
@executor 实现用户注册接口
@executor 重构数据库连接模块，添加连接池
```

**为什么用 Sonnet**：代码实现需要平衡质量和速度。Sonnet 够聪明，也够快。

**复杂任务可升级**：
```bash
@executor model=opus 重构整个认证模块
```

---

### debugger（调试者）

| 属性 | 值 |
|------|-----|
| **默认模型** | Sonnet（平衡） |
| **职责** | 根因分析、构建错误修复 |

调试者不是"试试看能不能修好"，而是"找到问题根因再修"：

- 分析错误堆栈
- 定位问题根因（不是表面症状）
- 提出修复方案
- 验证修复是否生效

```bash
@debugger 为什么 npm run build 失败了？
@debugger 用户登录时返回 500，帮我定位问题
```

**调试哲学**：头痛医头是不够的，要找到病根。

---

### verifier（验证者）

| 属性 | 值 |
|------|-----|
| **默认模型** | Sonnet（平衡） |
| **职责** | 完成验证、测试充分性确认 |

验证者是"验收官"，检查工作是否真正完成：

```
✓ BUILD: 编译通过
✓ TEST: 所有测试通过
✓ LINT: 无 lint 错误
✓ FUNCTIONALITY: 功能符合预期
✓ ARCHITECT: 架构审查通过
✓ TODO: 所有任务完成
✓ ERROR_FREE: 无未解决错误
```

**关键特性**：verifier 会要求**实际的命令输出作为证据**，不是"我觉得没问题"。

---

### tracer（追踪者）

| 属性 | 值 |
|------|-----|
| **默认模型** | Sonnet（平衡） |
| **职责** | 证据驱动的因果追踪、竞争假设分析 |

追踪者处理的是"不知道哪里出了问题"的情况：

- 收集证据和日志
- 建立因果假设
- 验证/排除假设
- 输出根因分析报告

```bash
@tracer 为什么有时候用户会话会莫名过期？
@tracer 数据库连接偶尔超时，帮我追踪原因
```

**与 debugger 的区别**：
- `debugger`：构建失败了，定位修复（已知错误）
- `tracer`：偶尔超时，追踪原因（未知原因）

## 🔍 审查通道

质量把关，发布前的最后一道防线。

### security-reviewer（安全审查员）

| 属性 | 值 |
|------|-----|
| **默认模型** | Sonnet（平衡） |
| **职责** | 安全漏洞、信任边界、认证/授权审查 |

审查范围：
- SQL 注入、XSS、CSRF
- 认证/授权漏洞
- 敏感数据泄露
- 信任边界问题
- 依赖库安全

```bash
@security-reviewer 审查认证模块的安全性
@security-reviewer 这个 API 有权限绕过风险吗？
```

---

### code-reviewer（代码审查员）

| 属性 | 值 |
|------|-----|
| **默认模型** | Opus（高质量） |
| **职责** | 全面代码审查、API 契约、向后兼容性 |

审查维度：
- 代码质量和可读性
- API 设计是否合理
- 向后兼容性
- 性能问题
- 错误处理

```bash
@code-reviewer 审查这个 PR 的所有变更
@code-reviewer 这个 API 设计是否向后兼容？
```

**与 security-reviewer 的区别**：security-reviewer 专注安全，code-reviewer 全面审查（包括安全）。

## 🎭 协调通道

这是 OMC 的独特设计——专门用来**挑战和质疑**。

### critic（批评者）⭐ 最重要

| 属性 | 值 |
|------|-----|
| **默认模型** | Opus（高质量） |
| **职责** | 计划和设计的差距分析、多角度审查 |

批评者的工作哲学：

> "一个计划只有在找不到任何漏洞时，才算通过。"

它会：
- 审查计划的完整性
- 发现设计中的漏洞
- 从多角度质疑方案
- 确保没有遗漏

```bash
@critic 这个架构设计有什么潜在问题？
@critic 这个执行计划有没有遗漏的边界情况？
```

**为什么 critic 很重要**：

- `planner` 可能遗漏细节
- `architect` 可能忽略约束
- `critic` 是最后的质量防线

在 Team 流水线中，critic 会在 plan 阶段后审查计划，发现问题会打回重做。这避免了"方向错了，执行得再好也没用"的情况。

## 智能模型路由

OMC 根据任务复杂度自动选择模型，不是所有任务都用最贵的模型：

| 层级 | 模型 | 适用场景 | 成本 |
|------|------|---------|------|
| LOW | Haiku | 快速查找、文档写作 | 低 |
| MEDIUM | Sonnet | 代码实现、调试、测试 | 中 |
| HIGH | Opus | 架构设计、战略分析、审查 | 高 |

**分配逻辑**：
- 高频、低复杂度 → Haiku（省钱）
- 日常开发工作 → Sonnet（平衡）
- 关键决策、质量把关 → Opus（保质）

这样既能保证质量，又能控制成本——**简单任务不浪费 Opus，复杂任务不用 Haiku 凑合**。

## 典型协作流程

一个完整的开发任务，Agent 们是这样协作的：

```
用户："实现一个完整的支付系统"

1. explore → 扫描现有代码，了解项目结构
2. analyst → 分析支付需求，发现合规约束
3. architect → 设计支付架构，定义接口
4. planner → 制定执行计划，拆解子任务
5. critic → 审查计划，发现遗漏（比如退款流程）
6. planner → 更新计划，补充退款流程
7. executor × 3 → 并行实现支付、退款、账单模块
8. test-engineer → 编写测试用例
9. security-reviewer → 安全审查
10. verifier → 验证所有功能
11. git-master → 创建语义化提交
12. writer → 编写 API 文档
```

**关键点**：critic 在第 5 步发现了遗漏，planner 在第 6 步修正——这就是多 Agent 协作的价值。单 Agent 可能会带着遗漏一路执行下去。

## 总结

OMC 的 19 个 Agent 不是简单的"功能拆分"，而是一套**模拟真实开发团队的协作体系**：

- **构建通道**：从探索到验证的完整开发链路
- **审查通道**：质量和安全的最后防线
- **领域通道**：按需调用的专业专家
- **协调通道**：专门挑刺的批评者

最精妙的设计是 **critic**——它不写代码，只负责质疑。但正是这种"挑刺"机制，让整个团队的输出质量大幅提升。
